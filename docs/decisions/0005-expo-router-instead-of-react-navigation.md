# 0005. Expo Router instead of React Navigation

- **Status:** Accepted
- **Date:** 2026-11-03
- **Deciders:** Igor Kazakov (drafted by Claude Code)
- **Related:** issues #257 (story), #258 (implementation), #259 (this ADR); supersedes
  [ADR 0002](0002-react-navigation-instead-of-expo-router.md); see also
  [ADR 0001](0001-nx-monorepo-and-claude-code-layout.md)

## Context

ADR 0002 (2026-10-20) replaced the scaffolded Expo Router with hand-written React Navigation 7
(component API), mainly to learn how navigation works underneath. The developer reversed that on
2026-11-03: file-based routing is familiar from the Next.js App Router, and the next stories (tabs,
detail screens, deep links) are cheaper to build when a route is "a file in a folder". Expo Router
is built on React Navigation, so stacks, tabs and params are the same concepts either way.

Facts from the implementation ([e60d0e0](https://github.com/IgorKazakovDev/GreetDay/commit/e60d0e0)):

- Typed routes (`experiments.typedRoutes` in `app.json`) generate `.expo/types/router.d.ts` and
  `expo-env.d.ts`. Both are git-ignored, and normally only the dev server generates them;
  `expo export` does not. A clean CI checkout therefore has no route types.
- Expo SDK 58's `expo-router` vendors React Navigation, so `@react-navigation/*` no longer needs to
  be a direct dependency. `ThemeProvider`, `DefaultTheme` and `Theme` are exported by `expo-router`.

## Options considered

### Option A: Stay on React Navigation 7 (ADR 0002)

- Pros: explicit navigators and param lists; nothing to regenerate.
- Cons: every screen touches two files (param list + navigator); deep links need a hand-written
  `linking` config; the developer no longer wants this trade-off.

### Option B: Expo Router with typed routes off

- Pros: no generated files, no CI step.
- Cons: `href` and `router.push()` accept any `string`, so a wrong path is a runtime bug. This
  loses the main safety benefit of the router.

### Option C: Expo Router with typed routes on, types generated by an Nx target

- Pros: wrong paths fail `typecheck`; CI needs no workflow change.
- Cons: relies on `expo customize` generating the types headlessly (see Decision).

## Decision

We choose **Option C**.

- **Routes are files in `apps/mobile/src/app/`.** `_layout.tsx` is the root layout (providers, then
  `<Stack>`), `index.tsx` is `/`. Route files only render a screen from `src/screens/`.
  Deep links (`greetday://…`) come from the file tree.
- **Typed routes on, generated by `mobile:typegen`.** A cached Nx target runs
  `expo customize tsconfig.json` with `CI=1` (headless and idempotent), and `typecheck` depends on
  it, so `nx affected -t typecheck` in CI works unchanged. Inputs: `src/app/**`, `app.json`,
  `package.json`; outputs: `.expo/types` and `expo-env.d.ts`.
- **`apps/mobile/tsconfig.json` `include`s the generated files** (`.expo/types/**/*.ts`,
  `expo-env.d.ts`). Without it `href` silently degrades to `string`. Expo's own tooling then finds
  `include` already satisfied and leaves the tsconfig alone. Because Nx's TypeScript sync would
  otherwise flip-flop the lib references depending on whether the generated files exist,
  `nx.sync.ignoredReferences` lists the three lib paths (`domain`, `design-tokens`, `contracts`),
  which keeps `nx sync:check` stable.
- **No direct `@react-navigation/*` dependencies.** Import from `expo-router`. Our `ThemeProvider`
  and the router's clash by name, so the router's is imported as `NavigationThemeProvider`.
- **Env validation stays first.** `index.ts` imports `./src/config/env`, then `expo-router/entry`.

## Consequences

- Positive: adding a screen is one route file plus the screen; deep links and typed `href` come for
  free; tabs will be a `(tabs)` layout; the mental model matches Next.js (`_layout.tsx` ≈
  `layout.tsx`, `index.tsx` ≈ `page.tsx`, `[id].tsx` ≈ dynamic segment, `(group)` ≈ route group).
- Negative / accepted trade-offs: every file in `src/app/` is a route, so tests, helpers and screen
  components live elsewhere (`src/screens/`, `src/router.spec.tsx`). Routing tests use
  `renderRouter` from `expo-router/testing-library`.
- Risk: typed routes in CI depend on `expo customize` generating the types. If an Expo upgrade
  changes that, `href` degrades to `string` without an error. After an Expo upgrade, check that a
  deliberately wrong `href` still fails `pnpm nx typecheck mobile`; if not, fix `mobile:typegen`.
- Follow-ups: E1-S2 builds the tab shell as a `(tabs)` layout. Typed params are read with
  `useLocalSearchParams`.
